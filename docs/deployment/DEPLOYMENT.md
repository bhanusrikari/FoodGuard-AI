# FoodGuard AI — Deployment Guide (Render + Vercel)

> **Model status reminder:** the deployed backend serves the same
> **SYNTHETIC DEVELOPMENT MODEL** described in `docs/ml/TRAINING_PIPELINE.md`
> and `README.md` — trained on deterministically generated synthetic
> images, not real food. It exists to prove the pipeline and Django
> integration work end-to-end in a real hosted environment. It is **not
> real-world validated** and must never be presented as evidence of
> FoodGuard's real accuracy. Real-world dataset acquisition, licensing, and
> holdout evaluation remain **NOT COMPLETED** (see `docs/datasets/`).

This guide only prepares/documents deployment. Nothing here has been
deployed as part of writing it.

---

## 1. Architecture

```
Vercel (frontend, static Vite build)
        │  HTTPS, VITE_API_URL
        ▼
Render Web Service (Django + gunicorn, native Python runtime)
        │
        ▼
Render PostgreSQL (managed)
```

## 2. One-time setup: Render PostgreSQL

1. Render dashboard → **New +** → **PostgreSQL**.
2. Name it (e.g. `foodguard-db`), pick a region, pick a plan (Free is fine
   to start).
3. Once created, Render shows an **Internal Database URL** — this is what
   the web service will use as `DATABASE_URL` (see below). You do not need
   to copy individual host/port/user/password values; `DATABASE_URL` alone
   is sufficient (`config/settings.py` parses it via `dj_database_url` and
   it takes priority over the individual `DATABASE_*` vars, which remain
   for local development only).

If you use `render.yaml` (see step 3), this database is created and linked
automatically — you can skip creating it by hand.

## 3. Deploying the backend to Render

### Option A — Blueprint (`render.yaml`, recommended)

1. Push this repo to a Git provider Render can access.
2. Render dashboard → **New +** → **Blueprint** → point it at this repo.
   Render reads `render.yaml` at the repo root and proposes the
   `foodguard-backend` web service + `foodguard-db` database.
3. Render will prompt for the `sync: false` variables it can't infer —
   fill in:
   - `DJANGO_ALLOWED_HOSTS` — the hostname Render assigns (shown before you
     confirm, e.g. `foodguard-backend.onrender.com`), plus any custom domain.
   - `DJANGO_CSRF_TRUSTED_ORIGINS` — `https://foodguard-backend.onrender.com,https://<your-vercel-app>.vercel.app`
   - `CORS_ALLOWED_ORIGINS` — `https://<your-vercel-app>.vercel.app`
     (add your Vercel custom domain too, once you have one)
4. Deploy. `DJANGO_SECRET_KEY` is auto-generated by Render
   (`generateValue: true`) — you never need to set or see it manually.

### Option B — Manual web service (no Blueprint)

1. Render dashboard → **New +** → **Web Service** → connect this repo.
2. Runtime: **Python 3**. Root directory: repo root.
3. **Build Command:**
   ```bash
   pip install -r requirements-render.txt && python manage.py collectstatic --noinput && python -m src.data.synthetic.generate_dataset && python -m src.ml.train --manifest data/synthetic/food_quality/manifest.jsonl --data-root data --output-dir models/food_quality --img-size 128 --epochs 12 --batch-size 16 --seed 20260927 --device cpu
   ```
4. **Start Command:**
   ```bash
   python manage.py migrate --noinput && gunicorn config.wsgi:application --bind 0.0.0.0:$PORT --workers 3
   ```
5. **Health Check Path:** `/healthz/`
6. Add the environment variables listed in section 5 below (link the
   Postgres instance you created in step 2 so Render injects
   `DATABASE_URL` automatically, under the service's **Environment** tab →
   **Add Environment Variable** → **Add from Database**).

## 4. Why the build trains a model

Model binaries are intentionally `.gitignore`d in this repo (see the
`.gitignore` comment block) — they are never committed. Rather than
carving out an exception and checking a binary `.pt` file into git
history, the build step regenerates the small, clearly-labeled
**synthetic development dataset** (`src/data/synthetic/`) and runs the
**real, unmodified** training pipeline (`src.ml.train`) against it. This:

- keeps the existing "never commit model binaries" convention intact,
- guarantees `AIAnalysisService` finds a real artifact at
  `FOOD_QUALITY_MODEL_DIR` and exercises the real inference path (not the
  mock fallback) on every deploy,
- takes about a minute on Render's build machine (verified locally: ~50s
  on CPU),
- is fully reproducible (fixed seed) and self-documenting — anyone reading
  the build log sees exactly where the model came from.

**If/when a real, food-trained model exists**, replace this build step
with one of:
- a Render **persistent Disk** mounted at `/opt/render/project/src/models`
  (Render disks require a paid instance type), populated once via
  Render's Shell tab, or
- fetching the artifact from external object storage (S3/GCS/etc.) as a
  build step, using a signed URL stored as a Render secret env var.

Either way, do **not** commit the real model to git; the placement
mechanism should stay separate from git regardless of which one you pick.

## 5. Render environment variables (full list)

| Variable | Required | Value |
|---|---|---|
| `DJANGO_SECRET_KEY` | Yes | Auto-generated by the Blueprint, or generate with `python -c "import secrets; print(secrets.token_urlsafe(50))"` |
| `DJANGO_DEBUG` | Yes | `False` |
| `DJANGO_ALLOWED_HOSTS` | Yes | Render hostname (+ custom domain), comma-separated |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Yes | Backend + frontend origins, comma-separated, full `https://` URLs |
| `CORS_ALLOWED_ORIGINS` | Yes | Frontend origin(s), comma-separated, full `https://` URLs |
| `DATABASE_URL` | Yes | From the linked Render Postgres instance (automatic via Blueprint or "Add from Database") |
| `AI_CONFIDENCE_THRESHOLD` | No (default 0.70) | Leave default unless you have a reason to change it |
| `TRANSLATION_PROVIDER` | No (default `none`) | Leave as `none` — no real provider is wired up |
| `SERVE_MEDIA_VIA_DJANGO` | No (default `True`) | Leave `True` unless you put an object store/CDN in front of `/media/` |
| `PYTHON_VERSION` | Recommended | `3.12.8` (or your matching local version) |

**Not needed on Render:** `DATABASE_NAME`/`USER`/`PASSWORD`/`HOST`/`PORT`
(superseded by `DATABASE_URL`), `FOOD_QUALITY_MODEL_DIR` (default already
matches where the build step writes the model).

## 6. Known Render limitation: ephemeral filesystem

Render's native web services do not persist local disk writes across
deploys (a new deploy = a new filesystem). This means:

- **Uploaded report images** (`MEDIA_ROOT`) written after a report is
  submitted will be lost the next time you deploy. This was already an
  documented MVP-scale limitation before this deployment prep (see
  `README.md`'s Deployment section) — it is not new, and not something
  this task's scope asked to fix (would require object storage, e.g. S3 +
  `django-storages`). Add a Render persistent Disk mounted at the app's
  `media/` directory if you need uploads to survive a redeploy, or accept
  the limitation for an MVP demo.
- **The synthetic model** is unaffected by this — it is *regenerated* on
  every deploy's build step (see section 4), so there's nothing to lose.

## 7. Deploying the frontend to Vercel

1. Vercel dashboard → **Add New** → **Project** → import this repo, set
   **Root Directory** to `frontend/`.
2. Framework preset: Vercel auto-detects Vite. Build command
   `npm run build` (this repo's `package.json` already runs `tsc -b && vite
   build`), output directory `dist`.
3. Project → **Settings** → **Environment Variables** → add:
   - `VITE_API_URL` = `https://<your-render-service>.onrender.com`
     (no trailing slash; set for Production, and again for Preview if you
     want preview deployments to hit the same backend).
4. `frontend/vercel.json` (added by this change) rewrites all paths to
   `/index.html` so client-side routes (`/admin`, `/reviewer/...`, etc.)
   don't 404 on a hard refresh or direct link — required because the app
   uses React Router's `BrowserRouter`.
5. Deploy.

## 8. CORS / CSRF — how the two sides connect

- The frontend calls the backend directly via `VITE_API_URL` — no proxy,
  no same-origin trick. That means the backend must explicitly allow the
  Vercel origin: set `CORS_ALLOWED_ORIGINS` (read by `django-cors-headers`)
  to the exact Vercel URL(s), including scheme (`https://`), no trailing
  slash, no wildcard.
- Auth uses JWT bearer tokens in the `Authorization` header (see
  `frontend/src/lib/http.ts` and `SIMPLE_JWT` in `config/settings.py`) —
  not cookies — so `CORS_ALLOW_CREDENTIALS` is correctly left unset
  (default `False`); nothing else to configure there.
- `DJANGO_CSRF_TRUSTED_ORIGINS` only matters for Django's own
  session/CSRF-cookie-based paths (the Django admin at `/admin/`, browsed
  from a browser) — include both the backend's own origin and the
  frontend's origin.

## 9. Post-deploy verification checklist

Run these against the real, deployed URLs (`$BACKEND` = Render URL,
`$FRONTEND` = Vercel URL):

```bash
# 1. Health check
curl -i $BACKEND/healthz/                       # expect 200 {"status": "ok"}

# 2. Registration + login
curl -i -X POST $BACKEND/api/v1/auth/register/ \
  -H "Content-Type: application/json" \
  -d '{"email":"verify@example.com","password":"VerifyMe!2026","password_confirm":"VerifyMe!2026","first_name":"V","last_name":"Test"}'

curl -i -X POST $BACKEND/api/v1/auth/login/ \
  -H "Content-Type: application/json" \
  -d '{"email":"verify@example.com","password":"VerifyMe!2026"}'
# capture the "access" token from the response for the next steps

# 3. Authenticated profile
curl -i $BACKEND/api/v1/auth/profile/ -H "Authorization: Bearer <access>"

# 4. AI analysis (requires a report with an image; via the frontend is
#    easiest — log in, create+submit a report with an image, run analysis,
#    and confirm the response includes predicted_class/confidence/risk and
#    an honest, non-fabricated message. Since this is the synthetic model,
#    a real food photo will most likely return HUMAN_REVIEW / low
#    confidence -- that is CORRECT behavior, not a bug: the model was
#    never trained to recognize real food.)

# 5. Roles: repeat steps 2-3 for each role you need to check (reviewer,
#    admin, restaurant user) using accounts created via Django admin
#    (/admin/) or `python manage.py createsuperuser` run once via Render's
#    Shell tab -- registration always creates CUSTOMER accounts by design.

# 6. Admin analytics (as an ADMIN or REVIEWER token)
curl -i $BACKEND/api/v1/analytics/summary/ -H "Authorization: Bearer <admin_access>"

# 7. Multilingual: open $FRONTEND, switch the language selector to
#    Telugu/Hindi, confirm UI text changes and persists on reload.
```

Then delete the `verify@example.com` account you created (Django admin, or
`python manage.py shell` via Render's Shell tab) so it doesn't linger as
test data in the production database.

## 10. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `ImproperlyConfigured: DJANGO_SECRET_KEY must be set...` on boot | `DJANGO_DEBUG=False` but `DJANGO_SECRET_KEY` unset/still the dev default | Set a real `DJANGO_SECRET_KEY` (Blueprint auto-generates it) |
| `Bad Request (400)` on every request | Render hostname missing from `DJANGO_ALLOWED_HOSTS` | Add the exact `*.onrender.com` hostname (no scheme, no path) |
| CORS error in browser console | Vercel origin missing/mismatched in `CORS_ALLOWED_ORIGINS` | Must be the exact scheme+host Vercel serves from, comma-separated if multiple, no trailing slash |
| `CSRF verification failed` (only relevant to `/admin/`) | Origin missing from `DJANGO_CSRF_TRUSTED_ORIGINS` | Add both backend and frontend origins with scheme |
| Infinite redirect loop / "too many redirects" | `SECURE_SSL_REDIRECT` fighting the proxy — should already be handled by `SECURE_PROXY_SSL_HEADER` (added in this change) | Confirm you didn't remove that setting; Render always terminates TLS in front of the app |
| AI analysis always returns mock (`mock-foodguard-ai`) results | Build step's training/generation command failed or was skipped, so `models/food_quality/model.pt` doesn't exist | Check the Render build logs for `src.data.synthetic.generate_dataset` / `src.ml.train` output; re-deploy |
| Build fails downloading ImageNet weights | Render's build network blocked `download.pytorch.org` | Not expected in normal Render builds (same domain family as the PyTorch wheel index already used); if it happens, this is an environment-specific network policy issue, not a pipeline bug — see `docs/ml/TRAINING_PIPELINE.md`. A `--no-pretrained-backbone` fallback exists in `src/ml/train.py` but was verified locally to under-fit within the default 12-epoch/3-epoch-freeze schedule for this task's synthetic dataset — using it well would need a `TrainingConfig` override (e.g. `freeze_backbone_epochs=0` and more epochs), which isn't exposed as a CLI flag today |
| Uploaded report images 404 after a while | Render's ephemeral filesystem (see section 6) — the image was written on one deploy's disk and is gone after the next | Expected MVP-scale limitation; add a persistent Disk or object storage if this matters for your use case |
| `relation "..." does not exist` after deploy | Migrations didn't run | Confirm the start command includes `python manage.py migrate --noinput` before `gunicorn` starts |
